Distributed Merge Sort with a Round-Robin Thread Pool

Individual assignment · Java · Submit your program and a report

1.The Task

You are given a large binary file of 64-bit integers. Sort it with a distributed merge sort: split the data into chunks, sort the chunks in parallel, then merge the sorted runs until one sorted output remains. All the work is done by a fixed pool of N worker threads. Every piece of work (sorting a chunk, or a merge) is a task, and the tasks are handed to the workers in round-robin order.

You will then measure how the running time, the memory use and the thread overhead change as N grows from 1 to 32, and explain what you see in a short report.

3.Input and Output Files

  • A data file is a plain binary file with no header. It holds n = (file size) / 8 values. Each value is a signed 64-bit integer (a Java long) stored in 8 bytes, little-endian.
  • Your output file must have the same format and size, with the values in non-decreasing order.
  • Read and write with java.nio: ByteBuffer.order(ByteOrder.LITTLE_ENDIAN) and a FileChannel. Be careful: DataInputStream and DataOutputStream are big-endian.

Name the main class DistributedMergeSort (file DistributedMergeSort.java). You may add more classes, but keep every .java file in one folder with no package line. Use only the JDK standard library. It will be compiled and run like this:

javac *.java
java -Xmx4g DistributedMergeSort <input-file> <output-file> <N>

The last line your program prints must be one result line in exactly this form (all times in milliseconds):

RESULT threads=8 n=134217728 read_ms=1101 sort_ms=3673 write_ms=598 total_ms=5373 peak_heap_mb=2067 cpu_ms=35530
Rules (breaking one costs marks under Implementation)
  1. Fixed pool. Start exactly N worker threads (1 ≤ N ≤ 32) once, reuse them for every task, and stop them at the end. Never start a thread per chunk or per merge. The main thread may read, write and coordinate, but it must not sort or merge.
  2. Round robin. Each worker has its own task queue. The i-th task submitted (counting from 0) goes to worker i mod N. Workers do not take tasks from other queues.
  3. Your own merge sort. No Arrays.sort, Arrays.parallelSort, Collections.sort, List.sort, sorted() or any other library sort. Insertion sort is allowed for pieces of at most 64 values.
  4. No ready-made parallelism. No ExecutorService / Executors, ForkJoinPool, CompletableFuture or parallel streams. You may use Thread, synchronized, wait/notify, locks, atomics, BlockingQueue, CountDownLatch and CyclicBarrier.
  5. Memory. The 1 GB file must sort within a 4 GB heap (-Xmx4g).
  6. Time limit. Every grading run must finish within 75 seconds on the instructor's machine, for any N. This is 3 times what a sample solution needs with one thread. A run that takes longer counts as failed.
Hints
  • A worker that waits for a task sitting in its own queue waits forever. Submit a merge only after both of its inputs are sorted (for example, one level at a time with a CountDownLatch).
  • Near the top of the tree there are few merges but each is large, so most workers sit idle (see the figure). A large merge can be cut into independent pieces using binary search. See Lecture 4 and CLRS (3rd edition) §2.3 for merge sort and §27.3 for multithreaded merge sort.

Run the 1 GB experiments on a lab machine. Sorting the 1 GB file needs over 2 GB of memory, which many laptops cannot spare, and the same machine for everyone makes your results easier to compare. The 1 MB experiments can run on your own computer.

Runs. For each file (1 MB and 1 GB) and each N = 1, 2, 4, 8, 16 and 32, run your program 5 times. Ignore the first run (the JVM is still warming up and the file is not yet cached) and report the median of the other four. Run Validate.java after every configuration and keep its output. The single-thread run on the 1 MB file is your baseline.

MetricHow to measure it
RuntimeWall-clock time of each phase (read, sort, write) and the total, with System.nanoTime(). From the sort times compute the speedup SN = T1 / TN and the efficiency EN = SN / N.

(c) Total CPU time (code below). (d) The extra thread-time N·TN − T1, which a perfect parallel program would keep at 0.
CorrectnessPASS from Validate.java for every file and every N, including your own edge-case files.

The JVM can report peak heap and CPU time itself, which works the same on every operating system:

import java.lang.management.*;

static double peakHeapMb() {          // largest heap use so far, in MB
    long sum = 0;
    for (MemoryPoolMXBean p : ManagementFactory.getMemoryPoolMXBeans())
        if (p.getType() == MemoryType.HEAP) sum += p.getPeakUsage().getUsed();
    return sum / (1024.0 * 1024.0);
}

static double cpuMs() {               // CPU time of all threads so far, in ms
    var os = (com.sun.management.OperatingSystemMXBean)
             ManagementFactory.getOperatingSystemMXBean();
    return os.getProcessCpuTime() / 1e6;
}
